# Release gate

Generated 2026-08-25.

Merging the code is not approval to run a live night. The previous spec said the app would be safe
once ten fixes landed, which was not supportable: the current live-game engine has never run a real
night, no host-role account has ever existed in production, nothing has been tested in a browser,
the Postgres harness had never been executed, and no deployment configuration had been inspected.

This is the list of evidence that has to exist before someone says yes. Each gate names who can
satisfy it. A gate marked blocking cannot be waived without the product owner saying so in writing.

## Delivery blocks

Each block is one reviewable changeset, independently deployable, with the database change and the
application change in a compatible order. The order is not negotiable in one respect: block 0 is CI
and the full migration replay, because those are what protect every auth and money migration that
follows.

### Block 0: Evidence pipeline: CI, full migration replay, and the test matrix

**Why here.** Developer review R09: the high-risk auth and money migrations in every later block must not land before the checks intended to protect them. The workflow, the replay and the npm scripts landed at adcce5d but have never been proved green on a runner, and Docker is unavailable on the dev machine, so the replay from empty and the Postgres function harness have literally never executed. Nothing else in this backlog can be verified until they have: every acceptance criterion here is stated as a database result, and there is currently no mechanism that can assert one. The test matrix belongs here too, because it is what ties each later block's claim of done to a specific assertion.

**Deployment.** No database change and no runtime change. Deployable at any time and independently. Sequence: get all three CI jobs green on a pull request, make replay.test.sql assert the live object, grant and RLS set read from bcmorqsgeumtmhvctvgu, prove a second replay changes no catalogue row, then turn on branch protection so no later merge is possible without it. Remove continue-on-error from the dependency-audit job as part of block 1, not here, so the gate turns green before it turns blocking. Confirm the runner can start Docker services before relying on npm run test:db; if it cannot, that is a block 0 failure, not a later surprise.

**Items.**

- `qual-ci-gate-and-migration-replay` (R0-blocker, M) Prove the CI gate green and make it blocking, including the full 28-migration replay
- `qual-money-and-live-path-test-coverage` (R0-blocker, L) Write the tests the money and live-game paths do not have, traced to the risks they cover

### Block 1: Auth foundation: close the door without locking staff out

**Why here.** Anyone on the internet can currently create an account that handle_new_user grants the host role, and user_role has no harmless tier, so every money and state defect further down this list is reachable by a stranger rather than by staff. Closing that is the single change that shrinks the threat model for everything after it, which is why it comes before the money work. The route guards, the invite and reset path, the cookie fix, the types and the Next upgrade are all in this block because none of them is safe to ship apart from the others: a pending tier with unguarded /host pages admits pending accounts, and a closed signup with no invite path is a cancelled night. The default-privilege and orphan-function revokes are here because they are the same posture question, asked at the schema level.

**Deployment.** Database first, app second, hosted Auth toggle last. (1) Migration A adds 'pending' to user_role in its own transaction, because Postgres will not let a new enum value be used in the transaction that adds it. (2) Migration B repoints handle_new_user at 'pending' and pins the profiles INSERT policy WITH CHECK to 'pending'. Both are backward compatible: existing admin and host rows are untouched and the running app never reads a role it does not know. (3) Deploy the app carrying the role checks on src/app/host/page.tsx and src/app/host/[sessionId]/[gameId]/page.tsx, the middleware fix that copies response.cookies onto all three redirect branches, the invite and password-reset path, the regenerated database types including UserRole 'pending', and next 16.3.2. (4) Only after an invite has been proved end to end, set disable_signup true in the hosted Auth settings; doing this before step 3 locks staff out. (5) Revoke the anon and PUBLIC default ACLs for functions and tables in schema public under both the postgres and supabase_admin grantors, and revoke PUBLIC and anon EXECUTE on create_table_booking_transaction; these touch no application code and can go last. Rollback: reverting the app leaves the pending tier in place and harmless; only step 4 needs undoing by hand.

**Items.**

- `sec-signup-grants-host-role` (R0-blocker, M) Anyone on the internet can create an account that is granted the host role
- `sec-host-routes-authorise-not-just-authenticate` (R0-blocker, S) The /host routes admit anyone with a session, so a pending account walks straight in
- `sec-staff-lifecycle-and-setup-endpoint` (R0-blocker, M) There is no defined way to invite, promote, disable or deprovision a staff account
- `sec-middleware-drops-refreshed-session-cookies` (R0-blocker, XS) Every redirect in the auth middleware throws away the refreshed session cookies
- `db-types-drift-from-live-schema` (R1-before-release, S) The hand-written database types claim a dozen live-nullable columns are non-null and list no enums
- `qual-prod-dependency-vulnerabilities` (R1-before-release, S) Five high-severity advisories in production dependencies, with next pinned exactly so no patch is picked up
- `sec-default-privileges-anon` (R1-before-release, S) Default privileges still hand anon EXECUTE on every new function and full DML on every new table
- `sec-orphan-booking-function` (R1-before-release, XS) An orphan SECURITY DEFINER function is anon executable and exists in production but in no migration

### Block 2: Money integrity at the moment of the win

**Why here.** Everything here decides whether a jackpot is awarded, to how many people, and for how much. It comes straight after auth because these are the defects that survive a trusted-account assumption: a forged winners row, a tie recorded as two full jackpots, a failed pot read that silently records a real jackpot as ineligible, a force button that pays the whole pot outside the window, and a pot whose max_calls can exceed 90 so the window never closes. The unique game index sits here because record_winner_atomic derives the stage from the game and the host screen derives last-game from the index, and the CHECK constraints ride in the same migration as the pot cap.

**Deployment.** App first, then database, which is the reverse of block 1 and deliberate. record_winner_atomic gains two new refusals (a second non-void is_snowball_jackpot row for a game, and a snowball Full House inside the window without an explicit true or false for p_snowball_eligible), so HOST_RPC_ERRORS and the host client must already carry the mappings and the pot-as-server-prop change or a host meets an unmapped raw Postgres error mid-claim. Then apply the migration: CHECK constraints on snowball_pots, game_states and winners, the unique index on games (session_id, game_index), the drop of the host arm of the winners INSERT policy, and the .eq('session_id', sessionId) guard for startGame's games lookup. All of it applies with no backfill: the 2026-08-25 preflight found zero duplicate (session_id, game_index) groups, zero pots over 90 calls, and clean data on every constrained column. Dropping the winners INSERT host arm is safe because record_winner_atomic is SECURITY DEFINER owned by postgres on a table without FORCE ROW LEVEL SECURITY. Rollback: the constraints, the index and the policy arm can each be reverted without touching a row of data.

**Items.**

- `sec-winners-insert-open-to-hosts` (R0-blocker, XS) A host can hand-craft a winners row straight through the API, fabricating a jackpot and forcing a pot reset
- `money-snowball-tie-double-jackpot` (R0-blocker, S) A tie on a snowball Full House records two full jackpots against a pot that pays once
- `money-pot-fetch-failure-withholds-jackpot` (R0-blocker, S) One failed pot fetch silently records a genuine jackpot win as not eligible
- `money-force-jackpot-ungated` (R0-blocker, S) Manual Snowball Win pays the full pot outside the call window, for any host, with no audit
- `money-pot-max-calls-unbounded` (R1-before-release, XS) Nothing caps a snowball pot's max calls at 90, so a typo opens the jackpot for ever
- `db-unique-game-index-per-session` (R1-before-release, S) Nothing stops two games in a session sharing a game order, and the host screen then thinks both are the last
- `sec-start-game-unvalidated-session-game-pair` (R1-before-release, XS) startGame runs as service role and never checks the game belongs to the session it is told to start

### Block 3: Close direct table writes so the RPC guards are binding

**Why here.** Block 2 hardens the functions; this block makes those functions the only way in. While a host holds table-wide UPDATE on game_states and sessions with role-only USING clauses and no WITH CHECK, every atomic guard added in block 2 can be walked around with a PATCH, so shipping block 2 without block 3 buys less than it looks. It comes after block 2 rather than before because narrowing the grants requires the replacement RPCs to exist first. The public read exposure and the UI-only session lock are here because they are the same question asked of reads and of the admin surface: what does an authenticated or anonymous caller actually get, as opposed to what the UI offers.

**Deployment.** Additive database change, then app, then narrowing, in three steps that must not be compressed. (1) Add SECURITY DEFINER functions guarded by assert_is_host() for the two writes startGame and maybeCompleteSession need (sessions.status and active_game_id), plus whatever remaining direct game_states writes require; additive, so the running app ignores them. (2) Deploy the app switching those call sites onto the functions, and switching createGame and duplicateGame onto the agreed session-lock rule. (3) Only then narrow the policies: add WITH CHECK, column-scope the UPDATE grants to the columns the remaining direct writes touch, replace the profiles SELECT policy with 'auth.uid() = id or caller is admin', and drop the redundant narrower game_states INSERT policy. Narrowing before step 2 breaks starting a game. The public-column decision (narrow the anon grants on sessions and games, or delete the four comments claiming a boundary that does not exist) is made here and applied in the same migration. Rollback at any step is a re-grant, which restores the previous behaviour immediately.

**Items.**

- `sec-game-states-update-unbounded` (R0-blocker, L) Hosts can rewrite any column of any game_states row, defeating the atomic call guards
- `sec-sessions-update-unbounded` (R0-blocker, M) Hosts can rewrite any column of any session, including the flag that switches off snowball settlement
- `sec-profiles-readable-by-every-account` (R2-next-cycle, XS) Every authenticated account can read the whole staff roster and who is admin
- `db-duplicate-game-states-insert-policy` (R2-next-cycle, XS) Two overlapping INSERT policies on game_states, the narrower one dead
- `live-public-anon-column-exposure` (R1-before-release, S) The narrow public SELECT lists are not a security boundary
- `admin-session-lock-server-side` (R2-next-cycle, S) The session lock on adding and cloning games is UI only, and Clone is not even disabled

### Block 4: Session and pot lifecycle: reset, delete, settle, void, correct

**Why here.** This is developer review R16 as one block: reset, delete, settle and void are four ways of unwinding the same money state and they must be designed together or there will be two different ways to reverse a settlement claim. It follows block 3 because the new admin RPCs need the narrowed policies to be meaningful, and it precedes the live-flow work because settlement is what the host's End Game control in block 5 will call. The pot-history display and the prize-write fix are here because they are the read side and the write side of the same records: a pot whose movements nobody can see, and a prize field the app overwrites and then locks.

**Deployment.** Additive RPCs first, app second, backfill last. (1) Migration adds delete_snowball_pot_safe, an admin pot-adjust RPC that writes snowball_pots and snowball_pot_history in one transaction under a for update lock on the pot and returns the persisted values, a retry path that settles an already-completed game, and the reset_session_safe changes (refuse when any game_states row for the session is in_progress read for update, reverse the settlement claim rows newest first under the pot lock, and record what was destroyed). All additive; the running app calls none of them. (2) Deploy the app in one release with the corrected confirmation copy, because today's reset modal promises a snowball-history deletion that does not happen and the corrected behaviour must ship with the corrected words. The admin void control, the void-after-settlement refusal, and the games.prizes write and edit changes go in this same app release. (3) The pot-history display ships after the write path is proved. (4) The opening-balance backfill for the six unlogged historic movements is written last, by hand, once the write path is stable, so a still-changing code path does not author the financial record. Rollback: the old direct .update() paths must not be restored under any circumstances, since they are the defect; roll back to the RPCs, never past them.

**Items.**

- `money-reset-session-unsafe-semantics` (R0-blocker, M) "Reset to Ready" wipes a live game and permanently strands the snowball pot
- `money-pot-delete-non-transactional` (R1-before-release, M) Deleting a snowball pot unlinks every game, then fails on a foreign key it cannot satisfy
- `money-admin-pot-write-not-atomic` (R1-before-release, M) Admin pot edits and resets are not proved to land and swallow their own audit failure
- `money-settlement-failure-no-retry` (R0-blocker, M) A failed pot settlement can never be retried because the game is already completed
- `money-void-after-settlement-pot-uncorrected` (R1-before-release, M) Voiding a jackpot winner after the game has settled leaves the pot wrong and the modal says otherwise
- `qual-session-reset-leaves-no-record` (R1-before-release, M) reset_session_safe deletes a whole night's winners and game states and records nothing
- `admin-no-void-winner-control` (R1-before-release, S) An admin reviewing a finished night has no way to void a wrongly recorded win
- `obs-snowball-pot-history-invisible-and-empty` (R1-before-release, M) The pot has grown 120 pounds with zero history rows, and no screen reads the history table at all
- `money-cash-jackpot-name-regex` (R1-before-release, XS) Starting any game whose name contains "jackpot" overwrites every stage prize

### Block 5: Live host mutations: idempotent, visible, and honestly completed

**Why here.** Now that the database refuses the wrong thing, the host's side of the conversation has to be trustworthy. Only recordWinner has a persisted idempotency key, yet the UI tells the host to retry after a transport failure, so a lost response on a committed call draws a second ball nobody announced and, on a snowball game, silently spends one call of the jackpot window. Ten handlers reset a busy flag in finally with no catch, so a dropped request looks identical to success. The completion and prove-the-write fixes are in this block rather than block 4 because they are the host-side call sites of the settlement work just landed, and the End Game control needs them to report the truth.

**Deployment.** Backward-compatible column first, three steps. (1) Migration adds a nullable client_request_id-style key column to the mutation functions' target rows plus a partial unique index where not null, and adds sessions.completed_at as a nullable column. An old client sending null keeps working throughout. (2) Deploy the app so it mints and sends keys, catches every mutation failure, refetches the winners lists explicitly after every mutation (never by adding public.winners to the supabase_realtime publication, per developer review R13, because winners.SELECT is granted to role public and publishing it would stream void_reason free text and client_request_id to every anonymous follower), and adds the unconditional End Game, the admin-only stage step-back, and the controller release plus admin force-takeover. (3) Only then make the functions require a key. The composite Continue-and-Take-Break must become one call before the idempotency work is judged done, otherwise a retry still advances two stages. Rollback: reverting the app leaves the key columns populated and inert.

**Items.**

- `live-mutation-protocol` (R0-blocker, L) One idempotent, version-checked mutation protocol for every host state change
- `live-host-mutation-failures-silent` (R0-blocker, S) Most host controls have finally but no catch, so a dropped request shows the host nothing
- `live-winner-lists-never-refresh` (R0-blocker, XS) The host's winners and prizes lists never update during a game
- `live-composite-advance-break-not-atomic` (R1-before-release, M) Continue and Take Break advances the stage before the break call, so a retry skips a whole stage
- `live-no-clean-end-or-abandon` (R1-before-release, M) A game can only be ended by recording a valid claim, and skipping the final stage leaves dangling state
- `live-stage-cannot-step-back` (R1-before-release, M) current_stage_index can only ever increase, so an accidental advance is unrecoverable
- `qual-completion-paths-report-false-success` (R0-blocker, S) endGame and maybeCompleteSession report success when the pot did not move or the session did not complete
- `qual-unproven-updates-report-success` (R1-before-release, S) Three .update() calls report success without proving the write landed, against the codebase's own rule
- `live-controller-lock-no-release` (R1-before-release, M) The controller lock can be taken but never released, so a second staff device can lock the host out

### Block 6: Host screen safety on a phone, in a noisy room

**Why here.** Every defect here turns a thumb slip into a money outcome, and each one needs the controls added in block 5 to already exist: the resume control, the confirmed skip and the view-only escape all describe states that block 5 created or made reachable. The claim grid is the sharpest of them, with 24 to 31px cells on a common phone, a called state distinguishable only by text opacity, and no read-back of what was selected before it is submitted as a valid claim.

**Deployment.** Client-only apart from the validateClaim de-duplication, which is a server action and needs no migration. Deployable independently and safe to ship in any order within the block. Acceptance is proved at the database, not on screen: a mis-tapped Skip must leave game_states.current_stage_index unchanged and insert no winners row; a duplicate-number claim must be refused before the membership loop; an ordinary Line win recorded after the Manual Snowball modal is cancelled must carry only the stage prize text in winners.prize_description. Verify the 44px targets at 360px width on the named host phone from the release gate, not in a desktop emulator.

**Items.**

- `qual-claim-entry-unsafe-on-a-phone` (R0-blocker, S) The claim grid has 27px targets, no read-back and no visible called state, so a mis-tap pays the wrong person
- `qual-paused-with-no-resume-control` (R1-before-release, XS) After Close and stay paused the host has no Resume control and the app's own copy points at one that does not exist
- `qual-skip-stage-no-confirm` (R1-before-release, XS) Skip (No Winner) sits 8px from Record Winner, is irreversible and has no confirmation
- `qual-view-only-lockout-no-way-forward` (R1-before-release, S) The View Only banner covers the current ball and offers no route back when another tab is still alive

- `qual-signout-on-live-host-screen` (R1-before-release, XS) Sign Out is a one-tap unconfirmed control in the top-right of the live host screen

### Block 7: Public screens survive a bad network

**Why here.** This is the only block that is entirely independent of the others, and the only one that would be worth shipping out of order if a live night were imminent, because it is what stops the pub TV and every punter phone reloading themselves into an error page during a wifi drop. It sits here rather than earlier because the readable-banner and full-board work depends on the honest state the earlier blocks produce; a legible banner over a wrong number is worse than an illegible one. The pounds-and-pence formatting is here because the surface it corrupts is the jackpot advertised on the TV.

**Deployment.** No database change; client-only; deployable at any time and revertible instantly. Ship the navigator.onLine guard, the modal and selection suppression, the poll request deadline and the time-decaying health state together, because each alone leaves a way for the screens to sit wrong: a guard without a deadline still lets one never-settling fetch stop polling for good, and a deadline without the guard still reloads an offline TV. The public server components must render a client recovery panel instead of calling notFound() on a read error, so error.tsx, global-error.tsx and not-found.tsx land in the same deploy. Verify at the database: after a simulated 90-second offline window, game_states_public.state_version must advance within one poll of the network returning, with zero reloads recorded on any of the three surfaces.

**Items.**

- `qual-offline-auto-reload-kills-every-screen` (R0-blocker, S) The 30-second auto-reload fires while offline and kills the pub TV, the phones and the host's claim
- `live-public-404-on-transient-read-failure` (R0-blocker, S) A transient read failure leaves the pub TV and every punter phone on a permanent 404
- `live-public-poll-can-hang-forever` (R1-before-release, M) The public poll has no request deadline and connection health never decays with time
- `qual-no-error-boundaries` (R1-before-release, S) No error.tsx, global-error.tsx or not-found.tsx anywhere, on screens that run unattended
